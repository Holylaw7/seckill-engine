## 1. 项目背景

### 1.1 业务背景

电商大促与热点商品场景下，开抢瞬间流量呈脉冲式爆发，可达秒级百万级请求。传统“数据库行锁 + 同步事务”链路在如此量级下会迅速打满数据库连接，导致 RT 飙升、雪崩甚至资损。

Seckill-Engine 定位为金融级高并发秒杀交易系统，核心矛盾是：**入口流量大、库存有限、订单必须准确**。系统需要在极端并发下做到：

- 挡住 90% 以上的非法/超量请求，保护核心链路；
- 库存预扣与扣减原子执行，杜绝超卖；
- 订单与库存最终一致，杜绝重复订单；
- 全链路可追踪、可审计、可回滚。

### 1.2 项目目标

| 目标 | 说明 |
| --- | --- |
| 高并发承载 | 支撑瞬时百万级入口流量，核心接口单集群 10,000 QPS 基线 |
| 零超卖 | 任意并发下库存不为负，成交数量 ≤ 场次库存 |
| 零重复订单 | 同一用户对同一场次仅生成一条有效订单 |
| 最终一致 | 库存预扣、订单落库、库存回补在 5 秒内收敛一致 |
| 高可用 | 核心链路可用性 ≥ 99.95%，故障可自动恢复 |
| 可演进 | 服务无状态、水平可扩展，为分库分表预留空间 |

### 1.3 项目范围

**包含：**

- 秒杀场次与活动配置；
- 入口保护（网关限流、IP/用户/API 限流、黑名单）；
- Redis 库存预扣与原子扣减（Lua）；
- 基于 RocketMQ 事务消息的异步订单链路；
- 订单生成、支付对接、超时关单、取消/退款；
- 库存回补与三方对账；
- 监控、日志、告警与审计。

**不包含（依赖外部系统）：**

- 商品主数据管理与完整电商后台；
- 营销优惠、积分、社区互动；
- 物流履约；
- 支付资金结算主体（由支付渠道完成）。

### 1.4 名词定义

| 名词 | 定义 |
| --- | --- |
| 秒杀场次 | 一次限定时间、限定库存的抢购活动 |
| 库存预扣 | 秒杀成功瞬间在 Redis 中锁定库存 |
| 最终一致 | 库存、订单、支付三方数据在短时间窗口内收敛一致 |
| 幂等 | 同一业务请求重复执行与执行一次结果相同 |
| 事务消息 | RocketMQ 半事务消息 + 本地事务 + 回查机制 |
| 回补 | 订单取消/超时后释放已锁定库存 |

## 2. 用户角色

| 角色 | 描述 | 核心权限与用例 | 优先级 |
| --- | --- | --- | --- |
| 匿名用户 | 未登录访客 | 浏览场次与商品详情；不可参与秒杀 | P1 |
| 注册买家 | 已登录用户 | 参与秒杀、查询结果、下单、支付、取消、退款申请 | P0 |
| 商家/运营 | 活动运营人员 | 创建/上下架场次、配置库存与限购、查看销售数据 | P1 |
| 平台管理员 | 系统运维与安全人员 | 风控规则、黑名单、限流参数、告警处置、灰度发布 | P1 |

- 运营与管理员操作需审计日志留痕。

## 3. 核心业务流程

### 3.1 秒杀主流程（P0）

```text
用户进入秒杀页
  → 登录与场次校验
  → Gateway 限流（IP / 用户 / API / 黑名单）
  → 风控校验（频次、设备、行为特征）
  → Redis Lua 原子预扣（检查库存 + 扣减一步完成）
  → 预扣成功：发送 RocketMQ 事务消息
  → 订单服务消费：幂等校验 → MySQL 落库
  → 用户查询秒杀结果（轮询/异步通知）
  → 15 分钟支付窗口内支付
  → 支付渠道回调 → 订单状态流转（待支付 → 已支付）
```

关键说明：

- **禁止数据库直接扣库存**，库存扣减只发生在 Redis（Lua 原子脚本）；
- 预扣成功即视为“抢到”，订单异步落库，用户无需等待事务完成；
- 秒杀结果以订单服务落库结果为准，Redis 预扣流水可对账。

### 3.2 库存回补流程（P0）

触发条件：支付超时关单、用户取消、退款成功、订单落库失败且已预扣。

```text
订单状态变更（关单/取消/退款）
  → 记录回补流水（幂等）
  → Redis 回补库存（Lua 原子）
  → 发送回补消息通知相关服务
  → 对账任务核对扣减/回补流水
```

### 3.3 对账流程（P1）

- 对账范围：Redis 扣减流水、订单表、支付流水；
- 周期：核心链路口径分钟级核对，全量日终对账；
- 差异处理：告警 + 冻结差异订单 + 人工处置，处置全程留痕。

### 3.4 异常与边界流程

| 场景 | 预期行为 |
| --- | --- |
| 库存不足 | 返回“已售罄”，不扣减、不产生订单 |
| 重复请求/重复提交 | 幂等处理，返回首次结果，不产生第二条订单 |
| 重复支付回调 | 幂等校验，订单状态不重复流转 |
| MQ 消息丢失 | 事务消息 + 重试 + 对账兜底，最终一致 |
| MQ 消息重复消费 | 消费幂等，重复消息不产生副作用 |
| Redis 故障 | 熔断降级，快速失败；禁止降级为数据库直接扣库存 |
| MQ 故障 | 秒杀快速失败并回滚预扣，避免“扣了库存没有订单” |
| 数据库故障 | 保护性降级，订单落库失败触发库存回补 |
| 支付渠道超时/回调丢失 | 主动查单 + 定时补偿 + 对账 |

### 3.5 业务规则（已冻结，需求基线 v1.0）

| 编号 | 业务规则 | 确认内容 |
| --- | --- | --- |
| BR-01 | 限购规则 | 默认每用户每商品限购 1 件；限购数可配置，后续支持扩展为 N 件 |
| BR-02 | 库存模型 | Redis 为热点库存层（预热 + 预扣），MySQL 为最终库存事实源 |
| BR-03 | 库存生命周期 | 商品库存初始化 → Redis 预热库存 → 秒杀开始 → Redis Lua 预扣库存 → 订单成功扣减 → 支付成功 → 最终库存确认 |
| BR-04 | 支付规则 | 支付超时 15 分钟；订单状态 WAIT_PAY → TIMEOUT，触发库存回补 |
| BR-05 | 一致性目标 | 业务最终一致 ≤ 5 秒；异常情况下允许人工补偿（补偿操作留痕、可审计） |
| BR-06 | 压测基准 | 库存 1,000、并发 10,000，验证 Redis Lua 原子扣减、零超卖、零重复订单、MQ 最终一致 |

### 3.6 订单状态机（已冻结）

状态集合：`CREATE`、`WAIT_PAY`、`PAY_SUCCESS`、`CANCEL`、`TIMEOUT`、`REFUND`

```text
CREATE → WAIT_PAY → PAY_SUCCESS
                 ├→ CANCEL（用户主动取消）
                 └→ TIMEOUT（15 分钟未支付）
PAY_SUCCESS → REFUND（退款成功）
```

| 当前状态 | 事件 | 目标状态 | 副作用 |
| --- | --- | --- | --- |
| CREATE | 订单生成完成 | WAIT_PAY | 进入支付等待窗口 |
| WAIT_PAY | 支付成功回调 | PAY_SUCCESS | 库存最终扣减确认 |
| WAIT_PAY | 用户取消 | CANCEL | 库存回补 |
| WAIT_PAY | 支付超时（15 min） | TIMEOUT | 库存回补 |
| PAY_SUCCESS | 退款成功 | REFUND | 库存回补 |

规则：

- 状态流转由订单服务统一管理，禁止非法跳转（如 TIMEOUT → PAY_SUCCESS）；
- 所有流转幂等，重复事件不改变终态；
- TIMEOUT / CANCEL / REFUND 均触发库存回补并记录回补流水。

## 5. 非功能需求

### 5.1 可用性

- 月度可用性 ≥ 99.95%（核心秒杀与订单链路）；
- 核心组件无单点，故障节点自动摘除；
- 关键故障场景具备预案并定期演练（Redis/MQ/DB/支付渠道）。

### 5.2 一致性

- 库存预扣采用 Redis Lua 原子执行，预扣阶段强一致；
- 订单与库存最终一致，窗口 ≤ 5 秒；
- 所有写链路具备幂等能力，重复执行无副作用。

### 5.3 安全

- 统一认证鉴权，接口防越权；
- 参数校验、防重放、支付回调验签；
- 接口防刷：按用户/IP/设备多维频次控制，验证码扩展接口预留；
- 用户黑名单：命中即拦截，支持运营维护与审计；
- 设备指纹预留：采集与识别能力为风控升级预留扩展点；
- 敏感数据加密存储与传输，日志脱敏；
- 关键操作审计留痕，符合个人信息保护与资金流水合规要求。

### 5.4 可扩展性

- 服务无状态，支持水平扩展；
- MQ 分区可扩容，消费能力随分区扩展；
- 数据库为分库分表预留空间，订单表按用户维度设计分片键候选；
- 配置中心化，参数变更可灰度、可回滚。

### 5.5 可观测性

- 结构化日志：入口/出口关键参数与耗时，全链路携带 TraceId，禁止敏感信息；
- 请求链路：TraceId 贯穿网关 → 秒杀服务 → MQ → 订单服务，一次请求可串联还原；
- 指标：QPS、RT（含 P99）、库存量（剩余/预扣/回补）、MQ 积压、线程池、JVM；
- 告警分级：P0 立即通知、P1 分诊处理、P2 日清。

## 6. 性能指标

| 指标 | 目标值 | 场景/说明 |
| --- | --- | --- |
| 入口峰值流量 | 100 万 QPS（瞬时） | 秒开瞬间全入口总流量 |
| 秒杀接口 QPS | ≥ 10,000 | 单集群基线（压测口径见验收清单） |
| P99 响应时间 | ≤ 200 ms | 预扣 + 秒杀结果返回链路 |
| 非法/超量请求拦截率 | ≥ 90% | 限流与风控生效验证 |
| 零超卖 | 库存不为负、成交 ≤ 库存 | 库存 1,000、并发 10,000 |
| 零重复订单 | 重复订单率 = 0 | 重复请求、消息重放场景 |
| 最终一致窗口 | ≤ 5 s | 预扣/订单/回补收敛时间 |
| 可用性 | ≥ 99.95% | 核心链路月度 |
| 恢复目标 | RTO ≤ 10 min，RPO ≤ 5 s | 核心数据故障场景 |
| 支付超时回补 | 15 min 内关单回补成功率 100% | 已支付订单除外 |

## 7. 风险分析

| 风险 | 等级 | 影响 | 缓解措施 | 跟踪阶段 |
| --- | --- | --- | --- | --- |
| 库存超卖 | 高 | 资损、客诉 | Redis Lua 原子预扣 + 唯一约束 + 对账 | 全阶段 |
| 重复订单 | 高 | 资损、客诉 | 幂等表 + 订单唯一索引 + 分布式锁 | 全阶段 |
| MQ 消息丢失/重复 | 高 | 数据不一致 | 事务消息 + 重试 + 幂等消费 + 对账兜底 | 全阶段 |
| Redis 故障 | 高 | 秒杀不可用/数据不一致 | 集群 + 熔断降级 + 预案演练 | Phase 2/5 |
| MQ 积压 | 中 | 订单延迟、体验劣化 | 分区扩容 + 消费压测 + 积压告警 | Phase 5/6 |
| 数据库瓶颈 | 中 | RT 上升、雪崩 | 异步化削峰 + 读写分离 + 分库分表预留 | Phase 2/6 |
| 恶意刷单/黄牛 | 中 | 资源浪费、公平性受损 | 限流 + 风控 + 黑名单 | Phase 3/5 |
| 支付回调丢失/延迟 | 中 | 订单状态不一致 | 主动查单 + 定时补偿 + 对账 | Phase 3/5 |
| 发布与配置变更 | 中 | 线上事故 | 灰度发布 + 配置中心 + 快速回滚 | Phase 7 |
| 各端时间不一致 | 低 | 开抢时间偏差争议 | 统一服务端时间源，前端倒计时仅作展示 | Phase 3 |
| 安全漏洞（越权/重放） | 中 | 数据泄露、资损 | 鉴权 + 验签 + 审计 + 安全测试 | Phase 3/5 |

风险登记约定：每阶段评审时更新风险清单，跟踪缓解措施落地情况，直到关闭。
