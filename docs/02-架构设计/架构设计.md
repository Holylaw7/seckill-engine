## 1. 设计目标与原则

### 1.1 设计目标

| 目标 | 对应需求 | 架构支撑 |
| --- | --- | --- |
| 入口瞬时百万级请求 | 性能指标 | Nginx + Gateway 多层限流，快速失败 |
| 秒杀接口 ≥ 10,000 QPS、P99 ≤ 200ms | AC-04/AC-05 | 无状态服务 + Redis 原子预扣 + MQ 异步削峰 |
| 零超卖 | AC-01 | Redis Lua 原子扣减，禁止 DB 直扣 |
| 零重复订单 | AC-02 | 幂等表 + 唯一索引 + 分布式锁 |
| 最终一致 ≤ 5s | AC-03 | RocketMQ 事务消息 + 消费重试 + 对账 |
| 可用性 ≥ 99.95% | AC-09 | 无状态多实例 + 故障降级 + 自动恢复 |

### 1.2 设计原则

1. 分层防护：流量在越靠前的层级被拦截，核心链路不承载无效流量；
2. 原子预扣：库存只经 Redis Lua 原子操作，MySQL 只做事实源落库与对账；
3. 异步削峰：预扣与下单解耦，MQ 消化峰值，用户通过结果查询感知；
4. 幂等兜底：消息、回调、重复请求全部幂等，异常可重放；
5. 演进式部署：开发单实例 → 测试哨兵 → 生产集群，同一套代码；
6. 可观测、可回滚：TraceId 贯穿，指标齐全，发布可灰度可回滚。

## 3. 微服务拆分方案

| 模块 | 职责 | 关键依赖 | 部署单元 |
| --- | --- | --- | --- |
| gateway | 统一入口：路由、限流（令牌桶+漏桶）、黑名单、鉴权前置 | Nacos、Redis、auth-service | 多实例无状态 |
| auth-service | 登录认证、会话、Risk 模块（防刷/黑名单/设备指纹预留/验证码扩展） | Nacos、Redis、MySQL | 多实例无状态 |
| seckill-service | 场次校验、Redis Lua 原子预扣、RocketMQ 事务消息发送、结果查询 | Nacos、Redis、RocketMQ | 多实例无状态 |
| order-service | 订单幂等落库、订单状态机、超时关单、取消 | Nacos、RocketMQ、MySQL | 多实例无状态 |
| inventory-service | 库存事实源、库存流水（扣减/回补）、对账支持 | Nacos、Redis、MySQL | 多实例无状态 |
| payment-service | 支付下单、渠道回调验签、主动查单、退款 | Nacos、MySQL、外部支付渠道 | 多实例无状态 |
| monitor | 指标暴露、健康检查、告警入口（Prometheus/Grafana 预留） | 各服务 | 独立部署 |
| common | 统一返回、全局异常、工具、常量、Snowflake 组件、Redisson 封装 | - | 依赖 jar |
| api | DTO/VO、跨服务接口契约（Feign 定义） | - | 依赖 jar |

通信方式：

- 核心交易链路：**异步 MQ**（seckill → order、order → inventory 回补、支付结果事件）；
- 管理/查询类：**同步 Feign**（网关调 auth 校验、运营查询）；
- 事件流：订单状态变更发布事件（order-status-change），库存回补与通知消费。

## 4. 技术选型说明

| 组件 | 选型 | 说明 |
| --- | --- | --- |
| 注册/配置中心 | Nacos 2.x | 注册发现 + 统一配置 + 动态刷新 |
| 微服务框架 | Spring Boot 3.x + Spring Cloud Alibaba | 与 Nacos/Sentinel 原生集成 |
| 网关 | Spring Cloud Gateway | 响应式网关，Redis 限流 |
| 缓存/库存 | Redis 7 + Redisson | Lua 原子扣减、分布式锁 |
| 消息 | RocketMQ 5.x | 事务消息、可靠重试、死信 |
| 存储 | MySQL 8.0 | 订单/库存事实源/流水 |
| ORM | MyBatis Plus 3.5.x | 数据访问 |
| 熔断降级 | Sentinel | 与 Nacos 动态规则集成 |
| ID 生成 | Snowflake（common 组件） | 全局有序 ID，预留集中发号服务 |
| 容器化 | Docker / Kubernetes | 演进式部署 |
| 可观测 | Micrometer + Prometheus + Grafana（预留） | 指标、Trace、告警 |

### 4.1 为什么选择 Nacos 2.x（与 Eureka/Consul 对比）

| 维度 | Nacos 2.x | Eureka | Consul |
| --- | --- | --- | --- |
| 服务注册发现 | 支持（临时实例 AP / 持久实例 CP） | 支持（AP） | 支持（CP） |
| 配置中心 | 支持，长轮询 + 动态推送刷新 | 不支持 | 支持（KV），变更能力与生态较弱 |
| 动态配置刷新 | 原生支持（@RefreshScope / Listener） | 无 | 需自行实现监听 |
| 性能与协议 | gRPC 长连接，2.x 性能显著提升 | HTTP 心跳，大规模心跳压力大 | Raft 同步，写放大 |
| 运维复杂度 | 中（自带控制台，命名空间/分组） | 低 | 中 |
| 生态 | Spring Cloud Alibaba 原生、中文社区活跃 | Netflix 2.x 已停止开发，1.x 仅维护 | 社区规模小 |
| 环境隔离 | 命名空间 + 分组（dev/test/prod） | 需自行设计 | KV 前缀隔离 |

**结论**：Nacos 2.x 一个组件同时解决注册发现、统一配置管理、动态配置刷新三个问题，且与 Spring Cloud Alibaba 生态集成成熟，支持三环境命名空间隔离，选型 Nacos 2.x。

## 5. 高并发链路设计

### 5.1 多层流量防护

| 层级 | 手段 | 目标 |
| --- | --- | --- |
| Nginx 层 | IP 维度限流、连接数限制、WAF 前置 | 过滤扫描与异常 IP |
| Gateway 层 | 令牌桶（IP/用户/API 维度）+ 漏桶（峰值整形）+ 黑名单 | 拦截 ≥ 90% 非法/超量请求 |
| 业务层 | Sentinel 熔断/降级、风控校验 | 保护核心服务 |
| Redis 层 | Lua 原子预扣，超卖/重复在缓存层终结 | 零超卖、零重复 |

### 5.2 限流算法

- **令牌桶**：按用户/API 维度配置速率，允许一定突发，平均速率受控；用于常规接口限流；
- **漏桶**：恒定速率放行，队列满立即拒绝；用于秒杀开场瞬间的峰值整形，防止瞬时流量打穿下游；
- 实现载体：Gateway 的 Redis RateLimiter + 自定义 Lua；规则通过 Nacos 动态下发。

### 5.3 快速失败策略

- 所有拒绝路径（限流、黑名单、未开场、售罄、重复抢购）**立即返回明确结果**，不占用下游资源；
- 不重试不可重试的请求（限流/风控拒绝），避免放大流量。

## 6. 数据流设计

### 6.1 秒杀主链路

```text
1  用户请求 → Nginx → Gateway
2  Gateway：限流 + 黑名单 + 风控前置（调用 auth-service Risk）
3  seckill-service：登录态、场次状态、资格校验
4  Redis Lua 原子预扣：
   检查库存 → 检查用户是否已抢 → 扣减库存 → 标记用户
   失败（库存不足 / 重复抢购）→ 快速失败返回
5  成功：生成 orderNo（Snowflake）→ 发送 RocketMQ 半事务消息
6  本地事务：记录预扣流水 → 提交消息
7  order-service 消费：幂等校验 → 订单落库（CREATE → WAIT_PAY）
8  用户查询秒杀结果（轮询 / 结果通知）
9  支付：payment-service 下单 → 渠道回调验签 → PAY_SUCCESS
10 对账：定时核对预扣流水 / 订单 / 支付
```

### 6.2 库存回补链路

```text
触发：WAIT_PAY → TIMEOUT（15min）/ CANCEL / REFUND / 订单落库失败
  → 记录回补流水（幂等，防重复回补）
  → Redis Lua 回补库存（校验回补后不超过总库存）
  → 发布库存回补事件
  → 对账任务核对扣减/回补流水
```

### 6.3 对账链路

```text
数据源：Redis 预扣流水 ｜ MySQL 订单表 ｜ MySQL 库存流水 ｜ 支付流水
  → 分钟级差异核对（核心链路） + 日终全量对账
  → 差异：告警 → 冻结差异订单 → 人工处置（留痕审计）
```

## 7. Redis 库存架构

### 7.1 部署形态演进

| 环境 | 部署形态 | 说明 |
| --- | --- | --- |
| 开发环境 | 单 Redis 实例 | 降低本地复杂度，快速迭代 |
| 测试环境 | Redis Sentinel（1 主 2 从 + 3 哨兵） | 验证高可用与故障切换 |
| 生产环境 | Redis Cluster（3 主 3 从起步） | 水平扩展、无单点、自动分片 |

演进理由：同一套代码从单实例到哨兵到集群，验证“开发到生产”的部署演进能力；客户端统一使用 Redisson 抽象，切换拓扑只改配置不改代码。

### 7.2 Redis Key 设计（提前冻结）

| Key | 类型 | TTL | 说明 |
| --- | --- | --- | --- |
| `seckill:session:{sessionId}` | Hash | 场次生命周期 | 场次元数据：开始/结束时间、状态、商品列表 |
| `seckill:stock:total:{skuId}` | String | 场次生命周期 | 总库存（预热写入，回补上限校验用） |
| `seckill:stock:{skuId}` | String | 场次生命周期 | 剩余可售库存（Lua 扣减） |
| `seckill:user:{userId}:{skuId}` | String | 场次结束 + 24h | 抢购标记（=1 表示已抢），防重复 |
| `seckill:lock:order:{userId}:{skuId}` | String | 10s | Redisson 防重复下单锁 |
| `seckill:blacklist:user:{userId}` | String | 长期 | 用户黑名单（网关/风控读取） |
| `risk:rate:{dim}:{value}` | String | 窗口期 | 频次计数（用户/IP/设备维度） |

分片扩展预留：

- 库存单 key 无法满足时，按商品分片：`seckill:stock:{skuId}:{slot}`；
- 分片 key 使用 hash tag（如 `{skuId}`）保证 Lua 多 key 操作落在同一槽位，保持原子性；
- 该扩展在 Phase 6 性能优化阶段按压测结果决定是否启用。

### 7.3 库存预热流程

```text
运营创建场次（MySQL 库存初始化）
  → 秒杀开始前 30 分钟预热任务触发
  → 读取 MySQL 库存 → 校验场次状态
  → 写入 seckill:stock:total:{skuId} 与 seckill:stock:{skuId}
  → 预热完成校验（总量一致）→ 场次状态置为 READY
  → 预热失败或对不上：告警 + 禁止开场（熔断）
```

规则：**未完成预热校验的场次不允许开抢**；预热只允许在秒杀开始前执行，开抢后禁止重置库存。

### 7.4 Lua 原子扣减设计

单次脚本调用内完成：库存检查、库存扣减、用户防重标记。设计逻辑（Phase 4 实现参考）：

```lua
-- KEYS[1] = seckill:stock:{skuId}
-- KEYS[2] = seckill:user:{userId}:{skuId}
-- ARGV[1] = userId, ARGV[2] = 限购数量(默认1), ARGV[3] = 标记TTL
1 若 KEYS[2] 已存在 → 返回 -2（重复抢购）
2 读取 KEYS[1]，不存在或小于 ARGV[2] → 返回 -1（库存不足）
3 DECRBY KEYS[1] ARGV[2]；SET KEYS[2] 1 EX ARGV[3]
4 返回 1（成功）
```

返回码约定：

| 返回 | 含义 | 处理 |
| --- | --- | --- |
| 1 | 预扣成功 | 生成 orderNo，发事务消息 |
| -1 | 库存不足 | 返回“已售罄” |
| -2 | 重复抢购 | 返回“请勿重复抢购” |

### 7.5 库存不足快速失败

- 场次状态、开抢时间在进入 Redis 前校验，未开始/已结束直接拒绝；
- 库存判断在 Lua 内原子完成，**无锁等待、无 CAS 重试循环**；
- 预扣失败不产生 MQ 消息、不写订单，失败成本极低。

### 7.6 库存回补

- 触发：TIMEOUT / CANCEL / REFUND / 订单落库失败回滚；
- 幂等：回补流水唯一约束（biz_type + biz_id），防止重复回补；
- Lua 回补：`INCRBY` 前校验回补后 ≤ `seckill:stock:total:{skuId}`，超过则告警；
- 再购策略：默认回补后允许用户再次抢购（删除用户标记），是否允许由场次配置控制（待 Phase 3 细化）。

### 7.7 库存监控

- 指标：剩余库存、已预扣量、回补次数、预扣成功率、单 key QPS；
- 告警：库存跳变异常、预扣成功率骤降、回补消息积压、预热校验失败；
- 对账：分钟级比对 Redis 扣减流水与 MySQL 订单/流水，差异告警。

## 8. RocketMQ 事务消息架构

### 8.1 Topic 与消息设计

| Topic | 用途 | 消息关键字段 |
| --- | --- | --- |
| `seckill-order-tx` | 预扣成功后异步建单（事务消息） | orderNo、userId、sessionId、skuId、quantity、预扣时间、traceId |
| `order-status-change` | 订单状态变更事件（回补/通知） | orderNo、status、原因、时间 |
| `seckill-result-notify` | 秒杀结果通知（预留） | orderNo、userId、结果 |

消息 Key 使用 `orderNo`（业务幂等键），Tag 按事件类型区分。

### 8.2 事务消息流程

```text
1 seckill-service 发送半消息（seckill-order-tx）
2 执行本地事务：写入预扣流水（与 Redis 预扣结果一致）
3 本地事务成功 → Commit 消息；失败 → Rollback 消息并回补库存
4 Broker 半消息超时 → 回查 seckill-service 本地事务状态
5 回查返回成功 → 继续投递；返回失败/未知 → 按策略回查直至最终态
```

回查接口必须幂等：以 `orderNo`/预扣流水为判定依据，不依赖内存状态。

### 8.3 消费与重试

- 消费组：`order-consumer`（order-service）；
- 消费幂等：幂等表 + 唯一索引 `uk(user_id, session_id, sku_id)`，重复消息直接返回成功；
- 重试：失败按延迟等级重试（默认 16 次），超过进入死信队列（DLQ）；
- DLQ 处理：告警 + 人工/半自动重放工具，重放仍幂等；
- 积压处理：积压指标告警 → 扩容分区/消费实例 → 必要时限流降级。

### 8.4 消息丢失与重复防护

| 风险 | 防护 |
| --- | --- |
| 半消息丢失 | Broker 持久化 + 回查机制 |
| 本地事务与消息不一致 | 事务消息保证：本地事务成功才投递 |
| 消费后宕机 | 消费位点未提交，重启后重投 |
| 重复投递/重复消费 | 消费幂等（唯一索引 + 幂等表） |
| 极端丢失 | 对账任务兜底（预扣流水无订单 → 补偿建单或回补） |

## 9. 数据一致性方案

### 9.1 一致性模型

- 强一致点：Redis Lua 预扣（单线程原子执行）；
- 最终一致：预扣 → 订单 → 支付/回补，窗口 ≤ 5 秒；
- 兜底：对账 + 人工补偿（留痕审计）。

### 9.2 幂等设计

| 层 | 幂等载体 |
| --- | --- |
| 请求层 | 业务流水号（orderNo）+ 幂等表（biz_type、biz_id 唯一） |
| 数据层 | 订单唯一索引 `uk(user_id, session_id, sku_id)` |
| 消息层 | 消费前查幂等表，重复消息直接 ack |
| 状态层 | 订单状态机非法跳转拒绝，重复事件无副作用 |

### 9.3 分布式锁（Redisson）

- 为什么需要：Redis Lua 已挡 Redis 层重复，但订单落库、超时关单、取消、支付回调存在并发状态变更，需要互斥保护；
- 场景：防重复秒杀（二道防线）、防重复订单、订单状态机并发流转；
- 粒度：`userId + skuId`（细粒度，不锁全局）；
- 超时：默认 10s（业务最长执行时间 + 余量），配合看门狗自动续期；
- 释放：finally 中释放，并校验持有者（防止误删他人锁）。

### 9.4 对账与人工补偿

| 差异类型 | 处置 |
| --- | --- |
| 有预扣、无订单 | 补偿建单（消息重放）或回补库存 |
| 有订单、无预扣 | 冻结订单 + 告警，人工核查 |
| 状态不一致（订单/支付） | 主动查单 + 定时补偿 |
| 库存流水不平 | 修复任务 + 人工审批 + 幂等流水 |

## 10. 订单 ID 设计

### 10.1 选型对比

| 方案 | 全局唯一 | 有序性 | 索引性能 | 扩展性 | 安全性 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| 数据库自增 | 单库内唯一 | 有 | 好 | 分库分表需全局方案，单点瓶颈 | 可枚举暴露业务量 | 不采用 |
| UUID | 有 | 无 | 36 字符、随机写入页分裂 | 好 | 不可枚举 | 不采用 |
| Snowflake | 有 | 趋势有序 | 好（B+ 树友好） | 本地生成、水平扩展 | 可反解时间（可接受） | **采用** |

### 10.2 Snowflake 结构

`1 bit 符号位 + 41 bit 毫秒时间戳 + 10 bit 机器 ID + 12 bit 序列号`，单机单毫秒可生成 4096 个 ID。

### 10.3 ID 生成服务设计

- 初期：作为 `common` 组件内嵌（每个服务实例本地生成，零 RPC 开销）；workerId 由 Nacos 配置/环境变量分配，保证实例唯一；
- 演进：预留独立 `id-service`（集中发号 + 号段批量预取），供未来多系统共用；
- 订单号规则：Snowflake 数值 + 业务前缀（如 `SO`），作为订单表主键与 MQ 消息 Key。

### 10.4 时间回拨处理

1. 记录本实例上次生成时间戳；
2. 回拨 < 5ms：自旋等待追平，继续服务；
3. 回拨 ≥ 5ms：**快速失败 + 告警**，禁止继续生成（避免 ID 重复），由监控介入（NTP 校正/实例隔离）；
4. 序列号溢出：等待下一毫秒。

## 13. 线程模型设计

### 13.1 Tomcat 线程池

- 默认 `max-threads=200`（压测后校准），秒杀接口开启独立限流，拒绝策略为快速失败；
- 请求线程不执行长事务、不阻塞等待 MQ/外部调用，避免线程耗尽。

### 13.2 异步线程池

| 池 | 建议参数 | 拒绝策略 | 说明 |
| --- | --- | --- | --- |
| 秒杀业务异步池（结果通知、回补执行） | core 50 / max 200 / queue 1000 | Abort + 告警 | 队列满快速失败，避免无界堆积 |
| 对账/补偿任务池 | core 10 / max 30 / queue 500 | CallerRuns | 低频任务，允许调用线程兜底 |

监控：活跃线程、队列深度、拒绝数作为指标上报。

### 13.3 MQ 消费线程

- `consumeThreadMin=20`、`consumeThreadMax=64`（按分区数与压测校准）；
- 消费逻辑必须幂等，单条消息处理不做长事务；
- 消费失败按重试策略进入延迟重试，**禁止无限循环重试阻塞队列**；
- 消费速率与 RocketMQ 分区数匹配，积压告警阈值 10 万条。

## 14. 缓存设计

### 14.1 缓存分层

- 本地缓存（Caffeine）：场次元数据等低频变化数据，短 TTL + 主动失效；
- Redis：库存（无 TTL，生命周期管理）、防重标记、限流计数、黑名单；
- 一致性：本地缓存只缓存可容忍短暂延迟的数据，库存类数据一律直连 Redis。

### 14.2 三大缓存问题

| 问题 | 应对 |
| --- | --- |
| 缓存穿透 | 布隆过滤器校验商品/场次存在性 + 空值短 TTL 缓存 |
| 缓存击穿 | 热点 key 互斥锁重建（Redisson）+ 逻辑过期；库存 key 由预热任务保障 |
| 缓存雪崩 | key TTL 随机抖动 + 多级缓存 + 限流保护；库存 key 不设 TTL，避免集中失效 |

## 15. 降级设计

| 故障 | 影响面 | 降级策略 | 恢复 |
| --- | --- | --- | --- |
| Redis 异常 | 预扣/防重/限流不可用 | 秒杀预扣**熔断快速失败，禁止降级为 DB 直扣**；查询降级本地缓存/DB | 哨兵/集群自动切换，Sentinel 熔断恢复后自动放量 |
| MQ 异常 | 建单链路中断 | 发送失败回滚预扣并回补；积压超阈值限流降级（部分请求直接失败） | 消息恢复后消费补偿，对账兜底 |
| MySQL 异常 | 订单/流水落库失败 | 订单落库失败触发库存回补 + 告警；查询走缓存 | 主从切换（未来），应用重试 |
| 支付渠道异常 | 支付不可用 | 保持 WAIT_PAY，定时查单，不自动关单误伤 | 渠道恢复后补偿 |

降级开关统一由 Nacos 动态配置下发，支持按环境、按场次灰度。

## 16. 故障恢复设计

| 场景 | 恢复方案 |
| --- | --- |
| 服务重启 | 优雅停机：下线注册 → 停止接收新流量 → 排空在途 MQ 消费 → 退出；就绪探针通过后才接流量 |
| 消息恢复 | DLQ 重放工具（幂等）；事务消息回查；对账任务对“有预扣无订单”补偿建单或回补 |
| 库存修复 | 对账发现差异 → 修复任务（补扣/回补）→ 人工审批 → 幂等流水留痕；支持库存快照对比 |
| 节点故障 | 无状态多实例自动摘除；Redis/MQ/MySQL 集群自动切换 |

故障演练（Redis 宕机、MQ 积压、DB 故障、单实例下线）列入 Phase 5 测试计划。
