| 项目 | 内容 |
| --- | --- |
| 文档版本 | v1.0（评审稿） |
| 状态 | 待评审 |
| 日期 | 2026-08-01 |
| 关联基线 | 需求基线 v1.0 / 架构基线 v1.0 |

---

## 1. 设计目标

1. **微服务数据库隔离**：每个服务拥有独立 database，禁止跨服务直接访问其他服务数据库；
2. **金融级准确性**：订单、库存、支付数据有唯一约束与不可变流水，支撑零超卖、零重复订单；
3. **可扩展性**：订单表预留 `user_id` 分片键，支持未来分库分表，主键全局唯一；
4. **可追踪可回滚**：所有核心表含审计字段，流水表只增不改，人工修复留痕；
5. **可演进**：初期单 MySQL 实例多 database，未来可平滑迁移独立实例与分片。

## 2. 方案选择

| 决策点 | 方案 | 理由 |
| --- | --- | --- |
| 隔离形态 | 单 MySQL 实例 + 每服务独立 database（`seckill_auth` 等） | 应用层物理隔离，避免跨库 JOIN；未来可按库迁移独立实例 |
| 主键 | Snowflake BIGINT | 全局唯一、趋势有序、分库分表友好（详见第 9 章） |
| 金额 | `DECIMAL(18,2)` | 精确十进制，禁止浮点 |
| 时间 | `DATETIME(3)` | 毫秒精度，满足对账与审计 |
| 状态 | `VARCHAR(20)` 枚举值 | 自描述、可扩展，配合状态机校验 |
| 软删除 | `deleted TINYINT` | 保留审计轨迹；流水表不使用软删除 |
| 并发控制 | `version` 乐观锁 | 库存事实表与订单更新防覆盖 |
| 有效订单唯一 | 可空唯一列 `active_key` | 同一用户同场次同商品仅一条有效订单，终态后可再购 |

## 3. 数据库与账号规划

| database | 归属服务 | 读写账号（最小权限） |
| --- | --- | --- |
| `seckill_auth` | auth-service | `auth_rw`（仅本库 DML） |
| `seckill_seckill` | seckill-service | `seckill_rw` |
| `seckill_inventory` | inventory-service | `inventory_rw` |
| `seckill_order` | order-service | `order_rw` |
| `seckill_payment` | payment-service | `payment_rw` |

规则：

- 每个服务的连接账号只能访问自己 database，账号由初始化脚本创建；
- 禁止跨库 JOIN、禁止应用直接跨库读写；
- DDL 按服务分目录版本化：`sql/{service}/V1.0__init.sql`。

## 4. auth-service 数据模型（seckill_auth）

表清单：`user`（用户表）、`user_auth`（用户认证表）、`risk_blacklist`（黑名单表）、`risk_record`（风控记录表）。

### 4.1 用户表 `user`

```sql
CREATE TABLE `user` (
  `id`            BIGINT       NOT NULL COMMENT '用户ID（Snowflake）',
  `username`      VARCHAR(64)  NOT NULL COMMENT '登录名',
  `password_hash` VARCHAR(128) NOT NULL COMMENT '密码哈希（BCrypt）',
  `phone`         VARCHAR(20)  DEFAULT NULL COMMENT '手机号（展示脱敏）',
  `nickname`      VARCHAR(64)  DEFAULT NULL COMMENT '昵称',
  `status`        TINYINT      NOT NULL DEFAULT 1 COMMENT '1正常 0禁用',
  `roles`         VARCHAR(64)  NOT NULL DEFAULT 'USER' COMMENT '角色（逗号分隔）：USER / USER,ADMIN',
  `created_at`    DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  `updated_at`    DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  `deleted`       TINYINT      NOT NULL DEFAULT 0 COMMENT '软删除',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_username` (`username`),
  KEY `idx_phone` (`phone`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='用户表';
```

### 4.2 用户认证表 `user_auth`

```sql

```

CREATE TABLE `inventory` (

  `biz_type`    VARCHAR(32)  NOT NULL COMMENT '业务类型：ORDER/CANCEL/TIMEOUT/REFUND/MANUAL',
  `biz_id`      VARCHAR(64)  NOT NULL COMMENT '业务ID（订单号等）',
  `operator_id` BIGINT       DEFAULT NULL COMMENT '人工修复操作人ID',
  `remark`      VARCHAR(256) DEFAULT NULL COMMENT '备注',

说明：流水是库存变更的唯一证据；`uk_biz` 保证同一业务事件（如同一订单回补）只产生一条流水，幂等防重复回补。

## 7. order-service 数据模型（seckill_order）

表清单：`seckill_order`（订单表）、`order_item`（订单明细表）、`idempotent`（订单域幂等表）。

### 7.1 订单表 `seckill_order`

```sql
CREATE TABLE `seckill_order` (
  `id`           BIGINT        NOT NULL COMMENT '主键=orderId（Snowflake）',
  `order_no`     VARCHAR(64)   NOT NULL COMMENT '业务订单号（SO+Snowflake）',
  `user_id`      BIGINT        NOT NULL COMMENT '用户ID（预留分片键）',
  `session_id`   BIGINT        NOT NULL COMMENT '秒杀场次ID',
  `sku_id`       BIGINT        NOT NULL COMMENT '商品SKU',
  `quantity`     INT           NOT NULL DEFAULT 1 COMMENT '数量',
  `order_amount` DECIMAL(18,2) NOT NULL COMMENT '订单金额',
  `order_status` VARCHAR(20)   NOT NULL DEFAULT 'CREATE' COMMENT 'CREATE/WAIT_PAY/PAY_SUCCESS/CANCEL/TIMEOUT/REFUND',
  `active_key`   VARCHAR(64)   DEFAULT NULL COMMENT '有效订单唯一键=user_id:session_id:sku_id，终态置NULL',
  `cancel_notify_status` VARCHAR(20) NOT NULL DEFAULT 'PENDING' COMMENT 'CANCEL_ORDER 发送状态：PENDING/SENT（v1.1 变更）',
  `pay_deadline` DATETIME(3)   DEFAULT NULL COMMENT '支付截止时间',
  `paid_at`      DATETIME(3)   DEFAULT NULL COMMENT '支付时间',
  `cancel_reason` VARCHAR(256) DEFAULT NULL COMMENT '取消/超时原因',
  `version`      INT           NOT NULL DEFAULT 0 COMMENT '乐观锁版本',
  `created_at`   DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  `updated_at`   DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  `deleted`      TINYINT       NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_order_no` (`order_no`),
  UNIQUE KEY `uk_active` (`active_key`),
  KEY `idx_user_status` (`user_id`, `order_status`),
  KEY `idx_user_session_sku` (`user_id`, `session_id`, `sku_id`),
  KEY `idx_status_deadline` (`order_status`, `pay_deadline`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='秒杀订单表';
```

关键设计说明：

- 主键 `id` 即 Snowflake 订单 ID，全局唯一，为未来分库分表提供天然支持；
- `active_key` 为可空唯一列：有效订单（CREATE/WAIT_PAY）写入 `user_id:session_id:sku_id`，进入终态（CANCEL/TIMEOUT/REFUND）置 NULL。MySQL 唯一索引允许多个 NULL，因此同一用户同一场次同一商品最多一条**有效**订单，终态后按场次配置允许再次购买；
- `idx_status_deadline` 支撑超时关单扫描（按状态 + 支付截止时间批量捞单）；
- `user_id` 为分片字段，所有订单查询必须携带 user_id。

### 7.4 active_key 生命周期与订单状态（冻结）

| 订单状态 | active_key | 说明 |
| --- | --- | --- |
| CREATE | 保留 | 订单已创建，购买资格占用中 |
| WAIT_PAY | 保留 | 支付窗口内继续占用，防止窗口内重复下单 |
| PAY_SUCCESS | 保留 | 支付成功，占用直至场次结束 |
| CANCEL | 释放（置 NULL） | 用户主动取消，库存回补后按场次配置允许再购 |
| TIMEOUT | 释放（置 NULL） | 支付超时关单，库存回补后按场次配置允许再购 |
| REFUND | 按业务策略 | 默认保留（退款仍计入限购，防止“退款-再抢”刷单）；若运营策略允许退款后再购，则释放并回补 |

原因说明：`active_key` 唯一索引保证**同一用户在同一秒杀场次同一商品最多只有一条有效订单**。保留（CREATE/WAIT_PAY/PAY_SUCCESS）期间任何重复下单请求都会命中唯一约束被幂等拦截；进入终态（CANCEL/TIMEOUT）后置 NULL 释放占用，配合库存回补支持按场次配置的再次购买；REFUND 默认保留占用，防止退款刷单。

状态变更与 active_key 更新必须在**同一事务**内原子完成（订单状态机更新 + active_key 置 NULL），避免“状态已终态但占用未释放”或反向不一致。

## 9. 主键设计：为什么订单不能使用自增 ID

| 维度 | 数据库自增 | UUID | Snowflake（采用） |
| --- | --- | --- | --- |
| 全局唯一 | 仅单库内唯一，分库分表需号段/全局表 | 全局唯一 | 全局唯一 |
| 有序性 | 单调有序 | 无序 | 趋势有序（时间前缀） |
| 索引性能 | B+ 树友好 | 随机值导致页分裂、索引膨胀 | 顺序写入，B+ 树友好 |
| 分库分表 | 需额外全局发号方案，有单点 | 无需协调 | 本地生成，天然支持 |
| 安全性 | 可枚举，泄露业务量 | 不可枚举 | 可反解时间（可接受，不泄露订单量） |
| 并发能力 | 单点瓶颈/锁竞争 | 无瓶颈 | 无中心化瓶颈 |

结论：自增 ID 在单库单体下简单，但秒杀系统必然走向分库分表，自增无法跨分片保证全局唯一，且高并发下存在锁竞争与可枚举风险；UUID 索引性能差。**订单主键采用 Snowflake 生成的 BIGINT**，全局唯一、趋势有序、分片友好。

## 10. 数据类型选择理由

| 类型 | 使用场景 | 理由 |
| --- | --- | --- |
| `BIGINT` | 所有主键、用户/场次/商品 ID | Snowflake 范围（2^63 内），避免字符串比较开销 |
| `DECIMAL(18,2)` | 金额 | 精确十进制运算，禁止 FLOAT/DOUBLE 存金额 |
| `INT` | 库存、数量 | 秒杀库存量级内足够，运算高效 |
| `VARCHAR(20)` | 状态枚举 | 自描述、可扩展，与状态机文档对应，避免魔法数字 |
| `VARCHAR(64)` | 订单号/流水号/消息 ID | 长度可控，索引友好 |
| `DATETIME(3)` | 时间字段 | 毫秒精度，满足对账与审计；应用统一时区 |
| `TINYINT` | 软删除/标志位 | 占用最小，语义明确 |
| `TEXT` | 渠道响应快照 | 仅低频审计数据使用，禁止用于业务查询字段 |

## 11. 索引与唯一约束汇总

| 服务 | 唯一约束 | 作用 |
| --- | --- | --- |
| auth | `uk_username`、`uk_user_auth(user_id,auth_type)`、`uk_blacklist(biz_type,biz_value)` | 防重复账号/重复黑名单 |
| seckill | `uk_session_sku(session_id,sku_id)`、`uk_message_id(message_id)` | 防重复配置、防重复预扣消息 |
| inventory | `uk_sku`、`uk_flow_no`、`uk_biz(biz_type,biz_id)` | 库存事实唯一、流水幂等 |
| order | `uk_order_no`、`uk_active(active_key)`、`uk_biz(biz_type,biz_id)` | 订单唯一、有效订单唯一、消费幂等 |
| payment | `uk_payment_no`、`uk_order(order_id)`、`uk_flow_no` | 支付单唯一、一单一付 |

查询索引设计原则：所有查询按分片键收敛（订单按 user_id）；状态扫描类查询（超时关单）使用组合索引；禁止无索引全表扫描。

## 12. 分库分表预留

- 分片键：`user_id`（订单表、明细表、支付表均冗余）；
- 分片策略：`hash(user_id) % N`（如 32 库 × 2 表），Phase 6/7 按数据量确定 N；
- 全局唯一：订单号/流水号由 Snowflake 生成，不依赖分片；
- 跨分片约束：业务查询必须携带 user_id；后台全量分析走离线数仓或索引表，禁止应用层跨分片扫表；
- 迁移路径：影子表双写 → 数据校验 → 灰度切换 → 双跑对账，全程可回滚。

## 13. 异常场景

| 场景 | 处理 |
| --- | --- |
| 唯一索引冲突（重复消息/重复下单） | 捕获 DuplicateKeyException，按幂等语义返回首次结果 |
| 预扣流水写入失败 | 本地事务回滚，事务消息 Rollback，Lua 回补库存 |
| 订单落库失败 | 消费重试；重试耗尽进 DLQ，对账兜底回补 |
| 回补与建单并发 | `stock_flow.uk_biz` + 订单唯一约束保证不重复 |
| 逻辑删除与唯一索引冲突 | 订单唯一性走 `active_key` 可空列，终态释放占用 |
| 分片迁移数据校验 | 影子表 + 校验任务（条数、金额、状态分布） |

## 14. 扩展方案

1. 独立实例迁移：按 database 一键迁移至独立 MySQL 实例；
2. 主从 + 读写分离：读流量走从库，延迟容忍设计；
3. 分库分表：按 `user_id` 分片，分片中间件统一接入；
4. 数据归档：终态订单按月归档至归档库/数仓，在线库只保留热数据；
5. 监控：慢 SQL、连接数、锁等待、主从延迟指标接入 monitor。

## 15. 乐观锁（version）使用范围（冻结）

| 表 | 版本字段 | 必须带版本校验的更新 | 说明 |
| --- | --- | --- | --- |
| `inventory` | `version` | 库存确认扣减、回补、人工修复 | 事实库存并发更新，防覆盖 |
| `seckill_order` | `version` | 订单状态流转（WAIT_PAY→PAY_SUCCESS/CANCEL/TIMEOUT、PAY_SUCCESS→REFUND） | 防止并发回调/关单互相覆盖，配合状态机校验 |
| `payment_order` | `version` | 支付状态更新（回调、关单、退款） | 防止重复回调与查单结果互相覆盖 |

更新范式（CAS）：

```text
UPDATE 表 SET status=?, version=version+1, ... WHERE id=? AND version=?
```

- 影响行数 = 1：更新成功；
- 影响行数 = 0：版本冲突 → 按幂等语义返回既有结果或告警，**禁止无版本校验的覆盖写**。

不适用版本校验的场景：流水表（只增不改）、幂等表（唯一索引兜底）、低频配置类表。

## 16. 库存最终一致模型（冻结）

状态转换：

```text
MySQL 库存（事实源）
  ↓ 预热（T-30min，校验一致后写入）
Redis 库存预热（seckill:stock:total:{skuId} + seckill:stock:{skuId}）
  ↓ Lua 原子扣减
Redis 扣减成功（写 seckill_pre_deduct 流水）
  ↓ RocketMQ 事务消息
订单成功（seckill_order 落库）
  ↓ 库存确认
库存确认（inventory 事实库存更新 + DEDUCT 流水）
```

异常与修复：

| 异常 | 判定 | 修复方式 |
| --- | --- | --- |
| Redis > MySQL | Redis 剩余库存高于 MySQL 可用库存（回补过头、确认缺失、重复回补） | 以 MySQL 为准：修复任务调低 Redis（校验 ≥ 0），写 REPAIR 流水 |
| Redis < MySQL | Redis 剩余库存低于 MySQL 可用库存（扣减未确认、人工改库、预热错误） | 以 MySQL 为准：修复任务调高 Redis（校验 ≤ total），写 REPAIR 流水 |
| 有预扣、无订单 | pre_deduct 存在，订单不存在 | 重投 CREATE_ORDER 或触发 STOCK_RECOVER 回补 |
| 有订单、无预扣 | 订单存在，预扣流水缺失 | 冻结订单 + 告警 + 人工核查 |
| 扣减/回补数量不平 | stock_flow 与 pre_deduct/订单对不上 | 修复任务 + 人工审批，写 REPAIR 流水 |

修复铁律：

- 一切校准以 MySQL 事实源为准，**禁止直接改 Redis**；
- 所有修复必须走 inventory-service 修复流程（repair 锁 + REPAIR 流水 + 审批留痕）；
- 修复后重新对账确认收敛，才可关闭告警。
