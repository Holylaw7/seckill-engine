## 2. 性能瓶颈分析

### 2.1 Gateway / HTTP 入口

| 项 | 内容 |
| --- | --- |
| 现象 | L-01 入口 avgRT 790ms / p99 1323ms；1000 并发下存在传输级连接拒绝（部分请求 -1） |
| 指标 | QPS 741；Tomcat 线程/accept 队列；p95/p99 波动 |
| 可能原因 | ① 测试模型每请求执行真实登录（BCrypt 验证）与 execute 串行，拉高入口 RT；② 单机 Testcontainers 与 1000 并发线程争抢 CPU；③ Gateway 未纳入端到端压测（Phase 5 按冻结设计绕过 Gateway），其 Netty/Filter/限流成本无实测数据；④ JDK HttpClient 连接复用已修复端口耗尽，但服务端队列仍受单实例容量限制 |
| 确认方式 | Phase 6.1 新增 Gateway 直连压测（对比经/不经 Gateway）；分离“登录+鉴权”与“execute 核心路径”两段计时；采集 Tomcat 线程池活跃数、Netty 事件循环、JWT 解析耗时（单测基准） |

### 2.2 Redis 秒杀链路

| 项 | 内容 |
| --- | --- |
| 现象 | L-02 10000 并发下 QPS 1847、p99 5154ms；正确性完全达标 |
| 指标 | 单次 Lua 扣减、连接数、commandstats |
| 可能原因 | ① Redis 单线程执行 Lua 本身为亚毫秒级，瓶颈更可能在 10000 线程调度/连接竞争；② Lettuce 共享连接池在极端并发下的等待；③ 单机 CPU 与 JVM 线程调度上限 |
| 确认方式 | `INFO commandstats` 统计 lua 调用次数与耗时；redis-benchmark 同机基线；按 1000/5000/10000 并发梯度复测；对比连接池大小参数 |

### 2.3 RocketMQ 链路

| 项 | 内容 |
| --- | --- |
| 现象 | 生产 3618 QPS 无压力；消费仅 ≈96.5 QPS，5000 条收敛 51.8s |
| 指标 | 消费 TPS、消费线程数、单消息 DB 事务耗时、broker 消费位点 |
| 可能原因 | ① 单 SKU DEDUCT 行锁（FOR UPDATE）串行化，是消费收敛的主要串行点；② order 建单每条消息 3~4 次 DB 写（幂等/订单/明细/确认）且单条事务；③ 消费者默认并发线程与逐条 ACK 模型；④ 单机 MySQL 与 RocketMQ 共享资源 |
| 确认方式 | 监控消费线程池大小与利用率；统计单消息建单+DEDUCT 事务耗时分布；对照多 SKU 并行消费（L-04-2 中 10 SKU 并行 DEDUCT 表现）；试验 consumeThreadNumber / 批量消费（评审后） |

### 2.4 Inventory 热点模型

| 项 | 内容 |
| --- | --- |
| 现象 | 历史上 confirmDeduct/recoverStock CAS 竞争均已在 Phase 5 修复（行锁串行化）；L-04 锁等待 18,839 |
| 指标 | 单 SKU 串行吞吐、行锁等待、CAS 重试 |
| 可能原因 | 行锁串行化保证正确性但限制单 SKU 吞吐；热点 SKU 的所有 DEDUCT/RECOVER 均落同一行 |
| 确认方式 | 单 SKU 消费吞吐上限实测（L-03 ≈96.5 QPS 中 DEDUCT 占比）；锁等待随并发梯度变化；对账口径复核（available+locked=total） |

### 2.5 MySQL 写模型

| 项 | 内容 |
| --- | --- |
| 现象 | TPS≈2605；row_lock_waits 18,839；慢 SQL 4,596；死锁 0 |
| 指标 | 每消息写次数、事务时长、热点行更新、慢 SQL 分布 |
| 可能原因 | ① 高频单行更新（inventory/order 状态）集中；② 流水表只增，写入量大；③ 慢 SQL 多为行锁等待排队所致；④ 索引与现有结构在只读验证下未发现结构性缺失（不改结构前提） |
| 确认方式 | slow_log 采样 top 语句 + EXPLAIN（只读）；事务平均时长统计；按表统计 Com_insert 增量占比 |

## 3. 优化目标

所有目标在 Testcontainers 同环境、同基线口径下可验证：

| 编号 | 目标 | 基线 | 目标值 |
| --- | --- | --- | --- |
| O-01 | MQ 消费吞吐 | ≈96.5 QPS | ≥300 QPS（3 倍） |
| O-02 | MQ 收敛时间（5000 条） | 51.8s | ≤25s |
| O-03 | MySQL 锁等待 | 18,839 | ≤9,500（-50%） |
| O-04 | 慢 SQL（>200ms） | 4,596 | ≤2,300（-50%） |
| O-05 | 秒杀入口 p99（登录+execute 模型分离后） | 1323ms | execute 核心路径 p99 ≤ 500ms |
| O-06 | Redis Lua 单请求延迟 | L-02 聚合口径 | 单次 Lua 调用 p99 ≤ 5ms（commandstats） |
| O-07 | 30 分钟稳定运行 | 190.4 QPS | ≥200 QPS 且 p99 ≤ 500ms |
| O-08 | 正确性门禁 | G-01~G-07 PASS | 优化后仍全部 PASS（零超卖/零重复/收敛/幂等） |

## 4. 优化方案

### 4.1 P0-1 MQ Consumer 吞吐优化

| 项 | 内容 |
| --- | --- |
| 名称 | MQ 消费并发与批处理优化 |
| 目标 | O-01 / O-02 |
| 涉及模块 | order-service、inventory-service（消费端与配置） |
| 收益 | 消费能力 3 倍；缩短最终收敛时间 |
| 风险 | 并发提升后行锁等待上升；批处理需保持逐条幂等语义 |
| 回滚方式 | 消费线程数/批大小回退为基线参数；批处理开关可配置 |
| 验证指标 | L-03 复测 consume QPS/收敛时间；锁等待与慢 SQL 监控；幂等专项回归 |

### 4.2 P0-2 Inventory 热点锁竞争分析

| 项 | 内容 |
| --- | --- |
| 名称 | 热点 SKU 行锁串行瓶颈确认与缓解 |
| 目标 | O-03 / O-01 |
| 涉及模块 | inventory-service |
| 收益 | 明确单 SKU 吞吐上限，为分片决策提供数据 |
| 风险 | 不破坏 available+locked=total 与对账口径 |
| 回滚方式 | 保持现有 FOR UPDATE 串行化，不做结构性变更 |
| 验证指标 | 单 SKU 并发梯度吞吐曲线；锁等待变化；对账 PASS |

### 4.3 P0-3 MySQL 锁等待优化

| 项 | 内容 |
| --- | --- |
| 名称 | 事务裁剪与热点写优化（不改表结构） |
| 目标 | O-03 / O-04 |
| 涉及模块 | order-service、inventory-service、payment-service |
| 收益 | 降低单消息事务时长与排队 |
| 风险 | 事务裁剪可能改变回滚范围，需保持状态机与幂等语义 |
| 回滚方式 | SQL/事务边界参数可回退 |
| 验证指标 | L-04 复测锁等待/慢 SQL；事务平均时长 |

### 4.4 P1-1 秒杀入口 RT 优化

| 项 | 内容 |
| --- | --- |
| 名称 | 入口链路分层测量与认证解耦 |
| 目标 | O-05 / O-07 |
| 涉及模块 | gateway、auth-service、seckill-service（测试模型与参数） |
| 收益 | 准确定位入口成本；execute 核心路径 p99 可观测 |
| 风险 | 不改变业务语义：登录仍真实执行，仅压测模型分离“登录”与“execute” |
| 回滚方式 | 压测模型可切换 |
| 验证指标 | Gateway 对比压测；两段 RT 分位数；Tomcat/Netty 资源指标 |

### 4.5 P1-2 Redis 连接与热点分析

| 项 | 内容 |

## 5. 优先级排序

### P0（必须优化）

1. MQ Consumer 吞吐优化（O-01/O-02）
2. Inventory 热点锁竞争分析（O-03）
3. MySQL 锁等待优化（O-03/O-04）

### P1（收益明显）

4. 秒杀入口 RT 优化与分层测量（O-05/O-07）
5. Redis 连接与热点分析（O-06）

### P2（长期优化）

6. SKU 分片库存模型（评审后）
7. 生产环境高 QPS 方案（Phase 5.8 衔接）

排序依据：P0 直接对应 L-03/L-04 已量化瓶颈；P1 依赖测试模型修正；P2 涉及模型/架构变更，须在 P0/P1 数据闭环后评审。

## 6. 不做事项

Phase 6.0/6.1 明确不进行：

- 修改接口契约、状态机、业务流程与业务语义；
- 修改数据库表结构、索引、唯一键；
- 修改 Redis Key 设计；
- 引入未经评审的新组件（新缓存、新 MQ、新框架）；
- 以性能优化为由放宽一致性/幂等/收敛门禁（G-01~G-07 保持）。

## 7. Phase 6 实施计划

### Phase 6.1 MQ 消费与入口测量

- 目标：O-01/O-02/O-05 测量闭环；
- 代码范围：order/inventory 消费端参数与批处理（评审后）、Gateway 压测与入口分层测量；
- 测试方式：L-03/L-01 复测 + 新增性能断言（consume QPS、收敛时间、execute p99）+ 全量回归（单元 281 / 集成 30 / 故障 13 / 压测 L-01~L-05）。

### Phase 6.2 锁等待与热点模型

- 目标：O-03/O-04；
- 代码范围：事务裁剪、SKU 分片可行性评审（若通过则进入设计）；
- 测试方式：L-04 复测（锁等待/慢 SQL 目标）+ 对账与故障演练回归。

### Phase 6.3 入口 RT 与生产容量衔接

- 目标：O-06/O-07 与 Phase 5.8 生产压测衔接；
- 代码范围：Redis 连接参数、生产容量方案评估；
- 测试方式：L-05 复测 + 生产/预发压测准备。

## 8. 评审标准

1. 所有优化均有 Phase 5 性能数据依据（第 2 节指标）；
2. 所有方案均完成收益/风险/回滚/验证指标评估（第 4 节）；
3. 无一项优化破坏一致性、幂等、最终收敛与状态机合法；
4. 无任何业务契约变更；
5. 每个优化都有可执行验证方案（第 3 节目标值）；
6. 评审通过后进入 Phase 6.1 编码。
