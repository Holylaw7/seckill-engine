# Seckill-Engine 开发规范

## 1. Git 分支模型（Git Flow）

| 分支 | 用途 | 规则 |
| --- | --- | --- |
| `main` | 生产稳定版本 | 禁止直接提交，仅由 `release/*` 合并 |
| `develop` | 开发主分支 | 功能分支合入目标 |
| `feature/*` | 功能开发 | 从 `develop` 切出，完成后合回 `develop` |
| `bugfix/*` | 问题修复 | 从 `develop` 切出 |
| `release/*` | 版本发布 | 从 `develop` 切出，合入 `main` 并打 tag |
| `hotfix/*` | 生产紧急修复 | 从 `main` 切出，合回 `main` 与 `develop` |

禁止直接修改 `main`；禁止无 commit 的大规模修改。

## 2. Commit 规范

格式：`type(scope): subject`

| type | 含义 |
| --- | --- |
| `feat` | 新增功能 |
| `fix` | 修复问题 |
| `refactor` | 重构 |
| `test` | 测试 |
| `docs` | 文档 |
| `perf` | 性能优化 |
| `chore` | 构建、工具、杂项 |

示例：`feat(inventory): 实现 Redis Lua 原子扣减库存`

要求：

- 提交前必须执行 `git status` 确认改动范围。
- 需求相关改动在 subject 中关联需求编号（如 `SEC-101`）。
- 每次提交保持单一职责，可独立回滚。

## 3. 代码分层规范

遵循阿里巴巴 Java 开发手册：

- Controller 不写业务逻辑，只做参数校验与协议转换。
- Service 负责业务编排与事务边界。
- DAO 只负责数据库访问，不承载业务。
- 接口入参出参使用 DTO/VO 分层，禁止实体直接暴露。
- 全局异常处理，统一返回对象，禁止裸返回。
- 日志规范：入口/出口打印关键参数与耗时；禁止打印敏感信息。
- 数据库表名、字段名统一规范；索引与 SQL 变更必须走版本化脚本。

## 4. 开发流程门禁

每个模块的开发必须按以下顺序执行，不可跳跃：

1. 设计说明（模块职责、数据流、接口、异常、幂等方案）
2. 设计评审
3. 编码实现（只开发当前模块）
4. Code Review
5. 添加并运行测试
6. Git 提交（独立 commit，输出 commit 编号）

## 5. 测试与质量门禁

- 单元测试：核心 Service 与工具类必须覆盖。
- 集成测试：数据库、Redis、MQ 联调。
- 并发测试：验证零超卖、零重复订单。
- 压力测试与故障测试：按 Phase 5 计划执行并输出报告。
- 未通过测试的代码禁止提交。

## 6. 可追踪与可回滚

- 所有代码修改可追踪到需求编号与 commit。
- 数据库变更使用版本化脚本，禁止手工改库。
- 每个发布版本在 `main` 打 tag，支持快速回滚。

## 7. Phase 4 编码工程规范（冻结）

1. **禁止一次生成全部代码**，按冻结顺序逐模块开发：
   `common → gateway → auth-service → seckill-service → inventory-service → order-service → payment-service`（monitor 随部署阶段）；
2. 每个模块严格执行：**设计确认 → 编码 → 测试 → Code Review → Git Commit**；
3. 提交格式：
   - `feat(module): xxx`（新增功能）
   - `fix(module): xxx`（问题修复）
   - `test(module): xxx` / `refactor(module): xxx` / `docs(module): xxx` / `perf(module): xxx`
   - `module` 为模块名（common/gateway/auth-service/seckill-service/inventory-service/order-service/payment-service）；
4. 每个模块独立 commit，禁止混模块提交；
5. 测试未通过不允许提交；每个模块提交后输出 commit 编号。
